## User Scenarios & Testing *(mandatory)*

### User Story 1 - 正常にログインしてダッシュボードへ進む (Priority: P1)

未認証ユーザーがメールアドレスとパスワードを入力し、認証に成功してダッシュボードへ到達できる。

**Why this priority**: ログイン画面の最重要価値は、既存ユーザーが迷わず自分の学習画面へ入れることにあるため。

**Independent Test**: 有効なメールアドレスとパスワードを入力し、送信後にダッシュボードへ遷移することを確認する。

**Acceptance Scenarios**:

1. **Given** 有効なメールアドレスとパスワードが入力されている, **When** 利用者がログインを実行する, **Then** セッションが発行されダッシュボードへ遷移する
2. **Given** 既にログイン済みである, **When** 利用者が `/login` を開く, **Then** ダッシュボードへ自動的にリダイレクトされる
3. **Given** 保護画面から未認証の状態で遷移してきた, **When** ログインに成功する, **Then** ダッシュボードへ遷移し、直前の保護画面に戻る導線が維持される

---

### User Story 2 - 新規登録してダッシュボードへ進む (Priority: P1)

利用者がメールアドレス、パスワード、確認用パスワードを入力し、新規登録に成功してダッシュボードへ到達できる。

**Why this priority**: 新規利用者が最初の学習導線へ入れることは、既存ユーザーのログインと同じく重要であるため。

**Independent Test**: 有効なメールアドレス、パスワード、確認用パスワードを入力し、送信後にユーザー作成とセッション発行が完了してダッシュボードへ遷移することを確認する。

**Acceptance Scenarios**:

1. **Given** 有効なメールアドレス、パスワード、確認用パスワードが入力されている, **When** 利用者がサインアップを実行する, **Then** ユーザー情報が DB に登録されセッションが発行されダッシュボードへ遷移する
2. **Given** 既に登録済みのメールアドレスが入力されている, **When** 利用者がサインアップを実行する, **Then** 汎用的な重複エラーが表示され、部分成功は残らない
3. **Given** サインアップ送信中である, **When** 利用者が再度送信操作を行う, **Then** 二重送信は発生しない

---

### User Story 3 - 入力不備を送信前に修正する (Priority: P1)

利用者がログインとサインアップの入力内容の不足や形式不正を送信前に把握し、画面上で修正できる。

**Why this priority**: 入力不備を早く止めることで、不要な認証失敗や再試行を避けられるため。

**Independent Test**: 空メール、形式不正メール、短すぎるパスワード、確認用パスワード不一致をそれぞれ入力し、送信前に項目近傍エラーが出て送信されないことを確認する。

**Acceptance Scenarios**:

1. **Given** メールアドレスが未入力である, **When** 利用者がログインしようとする, **Then** メール欄の近傍に必須エラーが表示され送信されない
2. **Given** メールアドレスの形式が不正である, **When** 利用者がログインしようとする, **Then** メール欄の近傍に形式エラーが表示され送信されない
3. **Given** パスワードが8文字未満である, **When** 利用者がログインしようとする, **Then** パスワード欄の近傍に長さエラーが表示され送信されない
4. **Given** 入力値の前後に空白が含まれている, **When** 利用者がログインしようとする, **Then** 空白を除いた値で検証される
5. **Given** サインアップ画面で確認用パスワードが一致しない, **When** 利用者がサインアップしようとする, **Then** 確認用パスワード欄の近傍に一致エラーが表示され送信されない

---

### User Story 4 - 認証失敗や通信障害から再試行する (Priority: P2)

利用者がログインやサインアップで誤った認証情報や一時障害に遭遇しても、原因を把握し再試行できる。

**Why this priority**: 失敗時に原因が分からないと離脱につながるため、回復可能性の提示が重要である。

**Independent Test**: 誤った認証情報、通信失敗、連続失敗による制限状態を再現し、適切な要約エラーと再試行導線が表示されることを確認する。

**Acceptance Scenarios**:

1. **Given** 誤ったメールアドレスまたはパスワードが入力されている, **When** 利用者がログインを実行する, **Then** 画面上部に汎用エラーが表示される
2. **Given** 通信障害が発生している, **When** 利用者がログインを実行する, **Then** 画面上部に要約エラーと再試行ボタンが表示される
3. **Given** 連続失敗により一時ロック状態になっている, **When** 利用者がログインを試みる, **Then** ロック解除までの残り時間と再試行可否が表示される
4. **Given** ログイン送信中である, **When** 利用者が再度送信操作を行う, **Then** 二重送信は発生しない
5. **Given** 既に登録済みのメールアドレスでサインアップを実行する, **When** 利用者が再試行せずに結果を確認する, **Then** 重複登録の詳細を出さずに汎用エラーが表示される

### Edge Cases

- メールアドレスの前後に空白がある場合は、送信前に trim した値で検証する
- 既にログイン済みの利用者が `/login` を直接開いた場合は、画面を見せずにダッシュボードへ遷移する
- 送信中はボタンを無効化し、利用者が重複送信できない状態にする
- 認証失敗時は、メールアドレスの存在有無やパスワード不一致の詳細を区別して表示しない
- スマートフォン幅でも横スクロールなしで主要操作が完了できる

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: システムはログイン画面にメールアドレス入力欄、パスワード入力欄、ログイン実行ボタン、新規登録画面への導線を表示しなければならない
- **FR-002**: システムはメールアドレスを必須項目として扱い、送信前に形式不正と空白除去後の有効性を検証しなければならない
- **FR-003**: システムはパスワードを必須項目として扱い、8文字以上64文字以下で検証しなければならない
- **FR-004**: システムは入力不備がある場合、送信を開始してはならず、該当項目の近傍にエラーを表示しなければならない
- **FR-005**: システムはパスワード表示切り替えを提供し、利用者が入力内容の表示・非表示を切り替えられなければならない
- **FR-006**: システムはログイン送信中に送信ボタンを無効化し、二重送信を防止しなければならない
- **FR-007**: システムは認証成功時にセッションを発行し、利用者をダッシュボードへ遷移させなければならない
- **FR-008**: システムは既に認証済みの利用者がログイン画面へアクセスした場合、ダッシュボードへ自動的にリダイレクトしなければならない
- **FR-009**: システムは未認証の保護画面アクセス時に `/login` へ誘導しなければならない
- **FR-010**: システムは認証失敗時に「メールアドレスまたはパスワードが正しくありません」という汎用エラーを表示し、認証情報の存在や不一致理由を区別してはならない
- **FR-011**: システムは通信失敗時に上部要約エラーと再試行導線を表示しなければならない
- **FR-012**: システムは連続失敗や制限状態に対して、残り時間と再試行可否を利用者が判断できる形で表示しなければならない
- **FR-013**: システムはログイン成功後に 24 時間有効なセッションを発行しなければならない
- **FR-014**: システムはログイン時の資格情報や個人識別情報を平文のまま記録してはならない
- **FR-015**: システムは本番環境では安全な通信経路のみを受け付け、開発環境ではローカル検証のための HTTP を許容できなければならない
- **FR-016**: システムはメール正規化値と送信元 IP の組み合わせで 1 分あたり 5 回を超えるログイン要求を拒否しなければならない
- **FR-017**: システムはキーボード操作のみでメールアドレス、パスワード、ログイン実行、主要導線へ到達でき、現在位置を視認できなければならない
- **FR-018**: システムはモバイル表示幅においても横スクロールなしでログイン操作を完了できなければならない
- **FR-019**: システムはエラー内容をスクリーンリーダーへ伝達できるようにしなければならない

### Key Entities *(include if feature involves data)*

- **LoginFormInput**: 利用者が入力する認証情報。属性はメールアドレス、パスワード、入力状態、表示切り替え状態。
- **AuthSession**: 認証成功後に発行される利用者セッション。属性は利用者識別子、発行時刻、有効期限、状態。
- **LoginErrorSummary**: 画面上部に表示されるエラー要約。属性はエラー種別、利用者向け文言、再試行可否、残り時間。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 有効な認証情報を入力した利用者の 95% 以上が、3 秒以内にダッシュボードへ到達できる
- **SC-002**: 入力不備がある試行の 100% で、送信前に項目近傍のエラーが表示される
- **SC-003**: 誤った認証情報による試行の 100% で、汎用エラーのみが表示され、存在有無や不一致の詳細は露出しない
- **SC-004**: 送信中の二重操作による重複認証要求が 0 件である
- **SC-005**: モバイル表示とキーボード操作の両方で、主要導線を使ったログイン完了率が 90% 以上である

## Assumptions

- 利用者はメールアドレスとパスワードによる認証を行う既存ユーザーである
- ログイン成功後の既定遷移先はダッシュボードである
- 認証済み利用者がログイン画面へ来た場合は、画面を見せずにダッシュボードへ誘導する
- パスワード再発行、SNS ログイン、多要素認証は今回の範囲外である
- 画面文言は日本語を基本とし、エラーメッセージは再利用しやすい形で管理する
- 開発環境では HTTP を許容するが、本番環境では安全な通信経路を前提とする
- 既存の保護画面判定とセッション管理の基本方針は親スペックに準拠する
- データ永続化は Prisma と PostgreSQL を使用する（Login/Signup の読み書きを永続化）
- 認証導線の改善は学習継続率の維持・向上に寄与する仮説のもとで評価し、ログイン/サインアップ成功率、再試行後の到達率、3 秒以内のダッシュボード到達率を指標とする
