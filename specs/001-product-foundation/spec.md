**Language Note**: この仕様書は原則として日本語で記述します（憲法: 実施言語）。

## 背景・目的

人間の記憶は時間とともに急速に薄れる（エビングハウスの忘却曲線）が、最適なタイミングで復習を行うと記憶は定着する。  
本アプリは「次に何をいつ復習すべきか」をシステムが自動提示することで、学習者の記憶定着率を継続的に改善することを目的とする。

| 項目 | 内容 |
|------|------|
| 対象ユーザー | 社会人学習者・学生 |
| 主な利用シーン | 毎日の復習計画確認、復習実施、進捗把握 |
| 解決する課題 | 復習タイミングの判断が難しく記憶定着が不安定になる問題 |
| コア価値 | 「今日やるべき復習」を迷いなく開始できる状態を提供する |

## MVP 範囲

### MVP に含む

| # | 機能 | 理由 |
|---|------|------|
| 1 | 学習カード登録・編集 | コンテンツ投入の起点 |
| 2 | 今日の復習一覧表示 | ユーザーが毎日使う中心機能 |
| 3 | 復習実施と結果記録 | 記憶定着の核心 |
| 4 | 次回復習日の自動計算（SM-2系） | アプリの差別化要素 |
| 5 | 週次進捗レポート | 継続モチベーション維持 |
| 6 | カテゴリ・タグ管理（カード一覧画面） | 学習カード整理性の向上 |
| 7 | 学習データのエクスポート/インポート | データ移行と運用継続性の確保 |

### MVP 外（Out of Scope）

- AI による問題自動生成
- 他ユーザーとのコンテンツ共有・マーケットプレイス
- 音声・動画コンテンツ対応
- 外部 LMS との連携（API 公開）
- プッシュ通知・メールリマインド通知（MVP外）
- 複数デバイス同期（MVP外）
- オフライン対応

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 今日の復習を開始する (Priority: P1)

学習者がアプリを開いたとき、今日実施すべき復習カードの一覧がすぐに表示され、迷わず復習を開始できる。

**Why this priority**: アプリの日々の起動動機そのものであり、これが機能しないとアプリの価値がゼロになる。

**Independent Test**: 復習期限を迎えたカードが少なくとも1枚登録された状態でダッシュボードを開き、一覧に表示されることを確認できる。

**Acceptance Scenarios**:

1. **Given** 今日期限の復習カードが3枚ある, **When** ダッシュボードを開く, **Then** 3枚が一覧に表示される（1秒以内）
2. **Given** 今日期限のカードがゼロ, **When** ダッシュボードを開く, **Then** 「今日の復習はありません」と次の予定日が表示される
3. **Given** ネットワーク障害中, **When** ダッシュボードを開く, **Then** エラーメッセージと再試行ボタンが表示される

---

### User Story 2 - 復習を実施して結果を記録する (Priority: P1)

学習者が復習一覧から1枚を選び、問いを見て答えを評価し、結果を記録することで次回復習日が自動更新される。

**Why this priority**: 記憶定着ロジック（SM-2系）の中心であり、アプリの差別化要素そのもの。

**Independent Test**: カードを1枚選択し「正解」を記録したとき、次回復習日が間隔計算ルールに従って更新されることを確認できる。

**Acceptance Scenarios**:

1. **Given** 復習カードを選択した, **When** 「正解（難易度: 易しい）」を記録する, **Then** 次回復習日が前回より長い間隔で設定される
2. **Given** 復習カードを選択した, **When** 「不正解」を記録する, **Then** 次回復習日が翌日に設定される
3. **Given** 復習記録を保存中にエラーが発生した, **When** リトライする, **Then** 同じ結果が正常に保存される（二重登録されない）

---

### User Story 3 - 学習カードを登録・編集する (Priority: P2)

学習者がキーワード・質問・答えを入力してカードを作成し、後から編集・削除できる。

**Why this priority**: コンテンツ投入がなければ復習機能も使えないが、P1と独立して実装・テスト可能。

**Independent Test**: カードを1枚作成し保存後、一覧に表示されることを確認できる。

**Acceptance Scenarios**:

1. **Given** 新規登録画面でタイトルと答えを入力した, **When** 保存する, **Then** カードが一覧に追加され最初の復習日が設定される
2. **Given** 既存カードを編集した, **When** 保存する, **Then** 変更内容が反映され復習スケジュールは維持される
3. **Given** カードを削除する, **When** 削除確認に応じる, **Then** カードと関連する復習ログが削除される

---

### User Story 4 - 週次進捗レポートを確認する (Priority: P2)

学習者が週ごとの復習実施率・正答率・継続日数を確認し、自分の学習状況を把握できる。

**Why this priority**: 継続モチベーションに直結するが、復習機能が先に成立していることが前提。

**Independent Test**: 1週間分の復習ログがある状態でレポート画面を開き、実施率が正しく計算されることを確認できる。

**Acceptance Scenarios**:

1. **Given** 直近7日間に5日復習した, **When** レポート画面を開く, **Then** 週の実施率71%（5/7）が表示される
2. **Given** 復習ログがゼロ, **When** レポート画面を開く, **Then** 「まだ復習記録がありません」と開始を促すメッセージが表示される

---

### User Story 5 - アカウントを登録してログインする (Priority: P3)

新規ユーザーがメールアドレスとパスワードで登録し、以降はログインして自分のカードと学習データにアクセスできる。

**Why this priority**: 他のストーリーが成立した後に必要になる基盤機能。単独で先行実装・テスト可能。

**Independent Test**: 新規メールアドレスで登録後、同一認証情報でログインでき、ダッシュボードが表示されることを確認できる。

**Acceptance Scenarios**:

1. **Given** 未登録のメールアドレスを入力した, **When** 登録を実行する, **Then** アカウントが作成されダッシュボードへ遷移する
2. **Given** 登録済みメールアドレスとパスワードを入力した, **When** ログインする, **Then** 自分のカード一覧が表示される
3. **Given** 誤ったパスワードを入力した, **When** ログインする, **Then** 「メールアドレスまたはパスワードが違います」と表示される（情報漏洩防止）

---

### Edge Cases

- 復習対象カードが 0 件のとき → 空状態メッセージと次の予定日を表示
- 同一カードへの同日二重回答 → 後勝ちで上書き、ログに両記録を残す
- 復習スケジュール計算中にエラー → 前回間隔を維持し、エラーをログに記録
- カード一覧で検索条件に一致する結果が 0 件 → 空状態メッセージと条件クリア導線を表示
- 大量カード（1000枚以上）登録時の一覧表示 → 無限スクロールで継続表示し、初回表示1秒以内
- 複数カードへの一括カテゴリ・タグ付与中に一部対象が更新済み → 変更済み分を除外し、処理結果を通知する
- インポートJSONの形式不正またはバージョン不一致 → 取り込みを中止し、既存データを変更しない
- インポート時にIDが衝突した場合 → 既存データは保持し、衝突レコードは新規IDを再採番して取り込む

### Functional Requirements

- **FR-001**: システムはメールアドレスとパスワードによるユーザー認証を提供しなければならない
- **FR-002**: システムはユーザーごとに学習カード（タイトル、問い、答え、メモ）を管理しなければならない
- **FR-003**: システムは毎日、各カードの nextReviewAt を基準に復習一覧を生成しなければならない
- **FR-004**: 復習結果記録後、SM-2系アルゴリズムで次回復習日と間隔日数を自動更新しなければならない
- **FR-005**: システムは週次の復習実施率・正答率・継続日数をユーザーに提示しなければならない
- **FR-006**: システムは学習データの削除確認を必須とし、誤削除を防止しなければならない
- **FR-007**: システムは復習スケジュール計算の根拠（間隔、難易度評価）をログとして保持しなければならない
- **FR-008**: 復習対象一覧は 100 件超の場合ページング処理を適用しなければならない
- **FR-009**: ユーザーは設定画面から復習間隔の初期パラメータ（初期間隔日数、EF初期値、EF最小値）を変更できなければならない
- **FR-010**: ユーザーはカード一覧画面からカテゴリ・タグを作成、編集、削除し、カードに関連付けできなければならない
- **FR-011**: ユーザーはカード一覧画面から学習データをJSON単一ファイルでエクスポートでき、学習カード登録画面からJSON単一ファイルをインポートできなければならない
- **FR-012**: 学習サイクル完了時、システムは当該サイクルデータをアーカイブし、必要に応じてアーカイブから復活して再開できなければならない
- **FR-013**: システムはインポート時にJSONスキーマとバージョンを検証し、不正ファイルの場合はデータを変更せずエラーを返さなければならない
- **FR-014**: システムはインポート時にID衝突を検知した場合、衝突レコードへ新規IDを再採番して取り込み、既存データを変更してはならない
- **FR-015**: ユーザーはカード一覧画面でタイトル、問い、答えを部分一致検索でき、カテゴリ・タグで絞り込み検索できなければならない
- **FR-016**: ユーザーは検索結果または一覧上で複数カードを選択し、一括でカテゴリ・タグを付与できなければならない
- **FR-017**: カード一覧はページングではなく無限スクロールで表示され、下端到達時に次の要素が連続表示されなければならない

## 画面一覧と画面遷移

### 基底画面

フロントエンドは、全画面共通の基底画面を持つ。基底画面は、画面上部のヘッダーメニュー部と、その下に配置されるページ表示部で構成する。

ヘッダーメニュー部は、左端からサービス名表示部とメニュー部を横並びで表示する。サービス名表示部には、サービスを示すアイコンとサービス名を表示する。メニュー部には、カード一覧、復習、設定画面へのリンクを均等割で表示する。

ヘッダーメニュー部のリンクをクリックしたとき、ページ表示部は該当する画面へ切り替わる。ページ表示部の初期表示はダッシュボードとする。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 復習一覧（100件以下）が1秒以内に表示される
- **SC-002**: 復習結果を記録後、次回復習日が画面上で即時更新される
- **SC-003**: 学習カード登録から最初の復習日設定まで3分以内に完了できる
- **SC-004**: 週次復習実施率が画面上で確認できる
- **SC-005**: ユーザーデータが他ユーザーから参照・変更されないことをテストで検証できる
- **SC-006**: 主要フロー（登録→復習実施→結果記録）の完了率を計測できる設計になっている
- **SC-007**: インポート時にID衝突が発生しても、既存データの欠損なく衝突データが再採番で取り込まれることをテストで検証できる
- **SC-008**: カード一覧でタイトル、問い、答え、カテゴリ、タグの条件を組み合わせて対象カードを絞り込める
- **SC-009**: 検索結果から複数カードを選択し、一括でカテゴリ・タグを付与できる
- **SC-010**: カード一覧は下端到達時に次の項目が追加表示され、1000件以上のカードでも閲覧を継続できる

## Assumptions

- ユーザーはスマートフォンまたはPCブラウザからアクセスする（ネイティブアプリMVP外）
- 復習間隔計算は SM-2系アルゴリズムを採用する（変更時は根拠と影響範囲を記録する）。初期パラメータはユーザーが設定画面からカスタマイズ可能とする
- 認証はメールアドレス＋パスワードを標準とし、SNSログインはMVP外
- 複数デバイス同期はMVP外とする（セッションは1デバイス同時ログインを前提とする）
- 学習データのエクスポート/インポート形式は JSON 単一ファイルを標準とする
- UIはモバイルファーストで、React + Tailwind CSS を使用する
- バックエンドは REST API を提供し、フロントエンドと分離する

## 制約・前提

- 個人情報保護法に準拠し、学習に不要な個人情報は収集しない
- 仕様策定・開発運用は原則として日本語で記述する
- Spec Kit の spec → plan → tasks の順で各サイクルを進める
- 1サイクルのタスク数が 15 以上になったら必ず分割する
