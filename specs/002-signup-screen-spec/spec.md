## Clarifications

### Session 2026-04-05

- Q: メール重複エラーの判定ルールはどれを採用するか → A: メールアドレスは trim 後に小文字化して一意判定する
- Q: 登録成功直後に発行するセッションの有効期限はどれにするか → A: 24時間有効
- Q: 登録 API のレート制限ルールはどれを採用するか → A: メール + IP 単位で 1 分あたり 5 回まで
- Q: アカウント作成成功後にセッション開始だけ失敗した場合の扱いはどれにするか → A: 登録全体を失敗扱いにしアカウント作成をロールバックする
- Q: パスワードの許容ルールはどれを採用するか → A: 8〜64文字、文字種の強制なし
- Q: SC-001（3分以内完了率90%以上）の公式判定期間はどれを採用するか → A: 週次集計（直近7日、母数100件以上）
- Q: SC-001 の母数から除外するケースはどれを採用するか → A: 利用者の明示キャンセルのみ除外し、それ以外は母数に含める

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 新規ユーザーが登録を完了する (Priority: P1)

未登録ユーザーがアカウント登録画面で必要項目を入力し、登録完了後にログイン済みの状態でダッシュボードへ到達できる。

**Why this priority**: 認証導線の起点であり、ここが機能しないと新規利用を開始できないため。

**Independent Test**: 未登録メールアドレス・有効なパスワード・一致する確認用パスワードを入力し、登録後にダッシュボードへ遷移し利用可能状態になることを確認する。

**Acceptance Scenarios**:

1. **Given** 未登録メールアドレスと有効なパスワードが入力されている, **When** 利用者が登録ボタンを押す, **Then** アカウントが作成され自動ログイン状態でダッシュボードへ遷移する
2. **Given** 送信中状態である, **When** 利用者が画面を確認する, **Then** 重複送信が防止され送信完了まで待機状態が明示される

---

### User Story 2 - 入力不備を即時に修正できる (Priority: P1)

利用者が入力内容の誤りを画面上で理解し、送信前に修正できる。

**Why this priority**: 入力不正のまま登録処理が進むと失敗体験と無駄な再試行が発生するため。

**Independent Test**: 空メール・短いパスワード・不一致パスワード確認を個別に入力し、項目近傍エラーが表示され、送信が実行されないことを確認する。

**Acceptance Scenarios**:

1. **Given** メールアドレスが未入力または形式不正である, **When** 利用者が登録を試みる, **Then** メール欄近傍にエラーが表示され登録処理は開始されない
2. **Given** パスワードが8文字未満である, **When** 利用者が登録を試みる, **Then** パスワード欄近傍に要件エラーが表示され登録処理は開始されない
3. **Given** パスワード確認が不一致である, **When** 利用者が登録を試みる, **Then** 確認欄近傍に不一致エラーが表示され登録処理は開始されない

---

### User Story 3 - 登録失敗時に再試行できる (Priority: P2)

利用者が重複メールや一時障害で登録できない場合でも、原因を理解し再試行に進める。

**Why this priority**: 失敗時の離脱を減らし、再入力コストを下げて登録完了率を維持するため。

**Independent Test**: 既存メールでの重複エラーと通信失敗を再現し、上部要約エラーと再試行導線が表示されることを確認する。

**Acceptance Scenarios**:

1. **Given** 既存メールアドレスである, **When** 利用者が登録を実行する, **Then** 登録は拒否され重複理由が理解できる文言で表示される
2. **Given** 登録送信時に一時的な障害が発生する, **When** 登録が失敗する, **Then** 画面上部に失敗要約と再試行導線が表示される
3. **Given** 未認証利用者が保護画面へ直接アクセスする, **When** システムがアクセスを判定する, **Then** 登録またはログインの導線へ誘導される

### Edge Cases

- メールアドレスに前後空白が含まれる場合は、判定前に正規化した値で形式検証する
- 登録ボタンが連続押下された場合、最初の1回のみを有効にして多重登録を防止する
- 登録失敗後、入力済み内容は保持し再入力負荷を下げる（機密性の高い表示はマスク状態を維持）
- アカウント作成とセッション開始のどちらか一方のみ成功する状態を許容せず、部分成功を残さない

## Requirements *(mandatory)*

### 画面デザイン参照

- アカウント登録画面のレイアウト、表示文言、状態例は [docs/signup-screen-ascii-ui.md](../../docs/signup-screen-ascii-ui.md) を正とする

### Scope Boundaries

#### In Scope

- アカウント登録画面のUI要件
- 入力バリデーション
- 登録成功時の遷移
- 登録失敗時のエラーハンドリング
- 登録後のセッション開始（自動ログイン）

#### Out of Scope

- ログイン画面自体の詳細仕様
- パスワード再発行
- SNSログイン
- MFA
- 複数デバイス同時ログイン

### Functional Requirements

- **FR-001**: システムはアカウント登録画面に、メールアドレス、パスワード、パスワード確認の3入力項目を表示しなければならない
- **FR-002**: システムはアカウント登録画面に、登録ボタンとログイン画面への遷移リンクを表示しなければならない
- **FR-003**: システムは画面状態として、初期、入力エラー、送信中、登録成功、登録失敗を利用者が判別できる形で提供しなければならない
- **FR-004**: システムはメールアドレスを必須入力とし、形式不正の場合は項目近傍にエラーを表示しなければならない
- **FR-005**: システムはパスワードを必須入力とし、8文字以上64文字以下かつ文字種の強制なしのルールで検証し、要件外の場合は項目近傍にエラーを表示しなければならない
- **FR-006**: システムはパスワード確認を必須入力とし、パスワードと一致しない場合は項目近傍にエラーを表示しなければならない
- **FR-007**: システムは入力不正が1件でもある場合、登録処理を開始してはならない
- **FR-008**: システムはメールアドレスを trim 後に小文字化した正規化値で一意判定し、既存メールアドレスによる登録要求を拒否して利用者が理解できる重複エラーメッセージを表示しなければならない
- **FR-009**: システムはサーバー側の失敗時、画面上部に要約エラーを表示し、再試行可能な導線を提供しなければならない
- **FR-010**: システムは登録成功時、24時間有効な利用者セッションを開始し、ログイン済み状態でダッシュボードへ遷移させなければならない
- **FR-011**: システムは既存ユーザー向けにログイン画面へ遷移できる導線を常時提供しなければならない
- **FR-012**: システムは未認証利用者が保護画面へアクセスした場合、登録またはログイン画面へ誘導しなければならない
- **FR-013**: システムは登録失敗時、既存データを変更してはならない
- **FR-014**: システムは利用者の認証情報を復元可能な平文形式で保持してはならない
- **FR-015**: システムは登録通信を安全な経路でのみ受け付けなければならない
- **FR-016**: システムはエラー記録に個人を特定できる情報や機密入力値を含めてはならない
- **FR-017**: システムは登録 API に対して、メールアドレス正規化値と送信元 IP の組み合わせ単位で 1 分あたり 5 回を超える要求を拒否し、再試行可能時刻を利用者が判断できる応答を返さなければならない
- **FR-018**: システムはアカウント作成とセッション開始を一貫した1処理として扱い、セッション開始に失敗した場合はアカウント作成をロールバックして登録全体を失敗として扱わなければならない

### Key Entities *(include if feature involves data)*

- **RegistrationFormInput**: 利用者が入力する登録情報。属性はメールアドレス、パスワード、パスワード確認、入力状態。
- **AccountRegistrationRequest**: 登録処理単位。属性は正規化済みメールアドレス、検証結果、受付時刻、処理結果。
- **UserAccount**: 登録済み利用者アカウント。属性は一意識別子、メールアドレス、認証情報、作成日時、状態。
- **UserSession**: 登録成功直後に開始される利用セッション。属性は利用者識別子、開始時刻、有効期限（24時間）、有効状態。
- **RegistrationErrorSummary**: 画面上部に表示する失敗要約。属性はエラー種別（重複/一時障害/その他）、利用者向け文言、再試行可否。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 直近7日間において、利用者の明示キャンセルのみを除外した母数100件以上の新規登録試行に対し、90%以上が登録画面到達から3分以内に登録完了しダッシュボードへ到達できる
- **SC-002**: 入力不備がある登録試行の100%で、対象項目近傍に理由付きエラーが表示され、送信は実行されない
- **SC-003**: 既存メールアドレスでの登録試行の100%が拒否され、利用者が次の行動を判断できる重複メッセージが表示される
- **SC-004**: 一時障害時の失敗ケースの95%以上で、失敗要約表示から1操作以内に再試行を開始できる
- **SC-005**: 登録処理の正常応答において95パーセンタイルが2秒以内に完了し、利用者が待機を許容できる

## Assumptions

- ダッシュボード画面は既に存在し、ログイン済み状態で遷移可能である
- ログイン画面は本仕様外だが、遷移先として利用可能である
- 登録画面はモバイル・デスクトップ双方で同等の主要導線（登録とログイン遷移）を提供する
- 本仕様で扱う認証方式はメールアドレスとパスワードのみとする
- 保護画面への未認証アクセス時の遷移判定は既存のアクセス制御ルールに準拠する
